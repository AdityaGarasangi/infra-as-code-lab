## Terraform `lifecycle` Meta Argument

- The `lifecycle` block is used to **control how Terraform creates, updates, and destroys resources**.
    
- It is **critical in production environments** to:
    
    - avoid downtime
        
    - prevent accidental deletion
        
    - handle external changes safely
        

---

## Syntax

```
resource "aws_instance" "web" {  
  ami           = "ami-123"  
  instance_type = "t3.micro"  
  
  lifecycle {  
    # lifecycle rules  
  }  
}
```
---

## 1️ `create_before_destroy`

- By default, Terraform follows:
```
Destroy → Create
```

- This can cause **downtime**.
    
- With `create_before_destroy`:
```
lifecycle {  
  create_before_destroy = true  
}
```
Terraform changes behavior to:
```
Create → Destroy
```
- New resource is created **before deleting the old one**.

---

### Example

```
resource "aws_instance" "web" {  
  ami = "ami-new"  
  
  lifecycle {  
    create_before_destroy = true  
  }  
}
```
- Prevents downtime when replacing instances.

---

## 2️ `prevent_destroy`

- Prevents Terraform from accidentally deleting a resource.
```
lifecycle {  
  prevent_destroy = true  
}
```
---

### Behavior

If you try:

terraform destroy

Terraform will throw an error:

Error: Instance cannot be destroyed

---

### Use Cases

- Production databases
    
- Critical infrastructure
    
- S3 buckets with important data
    

---

## 3️ `ignore_changes`

- Tells Terraform to **ignore specific attribute changes**, even if they differ from configuration.
```
lifecycle {  
  ignore_changes = [tags]  
}
```

---

### Example Scenario

- Someone updates tags manually in AWS console
    
- Terraform detects drift
    

Without ignore:

Terraform → revert changes

With ignore:

Terraform → ignores those changes

---

### Multiple Attributes

```
lifecycle {  
  ignore_changes = [  
    tags,  
    instance_type  
  ]  
}
```
---

### Ignore All Changes
```
lifecycle {  
  ignore_changes = all  
}
```

- Terraform will **never update the resource after creation**.
    

⚠️ Use carefully.

---

## 4️ `replace_triggered_by`

- Forces resource replacement when another resource changes.
```
lifecycle {  
  replace_triggered_by = [aws_security_group.sg]  
}
```

---

### Example

- If security group changes → EC2 instance is **recreated automatically**
    

Useful when dependency is **not directly linked in arguments**.

---

## Lifecycle Summary Table

|Argument|Purpose|
|---|---|
|create_before_destroy|Avoid downtime by creating new resource first|
|prevent_destroy|Protect critical resources from deletion|
|ignore_changes|Ignore specific attribute changes|
|replace_triggered_by|Force recreation when another resource changes|

---

## Important Behavior Notes

- `lifecycle` only affects **Terraform behavior**, not the actual resource config.
    
- Works **per resource**, not globally.
    
- Overusing lifecycle rules can make infrastructure **hard to manage**.
    

---

## Common Mistakes

- Using `ignore_changes = all` → Terraform stops managing resource
    
- Using `prevent_destroy` without understanding → blocks legitimate updates
    
- Overusing `depends_on` instead of proper references
    

---

## Must-Know Points

- `lifecycle` is essential for **safe production deployments**
    
- Helps control **downtime, drift, and accidental deletions**
    
- Most commonly used:
    
    - `create_before_destroy`
        
    - `prevent_destroy`
        
    - `ignore_changes`

---

|Argument|Description|
|---|---|
|create_before_destroy|Creates the new resource before destroying the old one to avoid downtime.|
|prevent_destroy|Prevents accidental deletion of a resource; Terraform will throw an error if destroy is attempted.|
|ignore_changes|Ignores changes to specified attributes during updates (helps avoid drift corrections).|
|replace_triggered_by|Forces resource replacement when specified resources or attributes change.|
