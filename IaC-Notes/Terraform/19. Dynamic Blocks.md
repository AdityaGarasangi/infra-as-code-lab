- **Dynamic blocks allow you to generate nested blocks dynamically using loops.**
- They are used when a **resource requires repeated nested blocks**, but the number of blocks **is not fixed**.

Instead of manually writing many blocks like this:

```
ingress {
  from_port = 80
  to_port   = 80
  protocol  = "tcp"
}

ingress {
  from_port = 443
  to_port   = 443
  protocol  = "tcp"
}
```

You can generate them **dynamically using a loop**.

---

### Why Dynamic Blocks Are Needed

Some Terraform resources contain **nested configuration blocks**, not arguments.

Example:

```
resource "aws_security_group" "web" {
  name = "web-sg"

  ingress { ... }
  ingress { ... }
}
```

Here `ingress` is a **block**, not a normal attribute.

You **cannot use normal loops like `for_each` directly inside blocks**.

This is where **dynamic blocks solve the problem**.

---

# Dynamic Block Syntax

Basic syntax:

```
dynamic "<block_name>" {
  for_each = <collection>

  content {
    # block configuration
  }
}
```

Explanation:

|Part|Meaning|
|---|---|
|dynamic|Terraform keyword to generate blocks|
|block_name|Name of the block being generated|
|for_each|Collection to iterate|
|content|Actual block body|

---

# Example 1 — Dynamic Security Group Rules

Without dynamic blocks:

```
resource "aws_security_group" "web" {
  name = "web-sg"

  ingress {
    from_port = 80
    to_port   = 80
    protocol  = "tcp"
  }

  ingress {
    from_port = 443
    to_port   = 443
    protocol  = "tcp"
  }
}
```

This becomes repetitive.

---

Using dynamic block:

```
variable "ports" {
  default = [80, 443]
}
```

```
resource "aws_security_group" "web" {
  name = "web-sg"

  dynamic "ingress" {
    for_each = var.ports

    content {
      from_port = ingress.value
      to_port   = ingress.value
      protocol  = "tcp"
      cidr_blocks = ["0.0.0.0/0"]
    }
  }
}
```

Terraform automatically generates:

```
ingress { port 80 }
ingress { port 443 }
```

---

# How `ingress.value` Works

Inside the dynamic block:

```
for_each = var.ports
```

Terraform creates an iterator object named **after the block**.

So:

```
ingress.value
```

means the **current item from the loop**.

Example values:

```
80
443
```

# Example 2 — Multiple Security Rules with Map

Using just ports is limited.

Better approach:

```
variable "ingress_rules" {
  default = [
    {
      port        = 80
      description = "HTTP"
    },
    {
      port        = 443
      description = "HTTPS"
    }
  ]
}
```

Dynamic block:

```
resource "aws_security_group" "web" {

  dynamic "ingress" {
    for_each = var.ingress_rules

    content {
      from_port   = ingress.value.port
      to_port     = ingress.value.port
      protocol    = "tcp"
      description = ingress.value.description
      cidr_blocks = ["0.0.0.0/0"]
    }
  }
}
```

Generated blocks:

```
ingress { port 80 }
ingress { port 443 }
```

# Example 3 — Dynamic EBS Volumes

Some resources require multiple nested blocks.

Example:

```
resource "aws_instance" "server" {

  ami           = "ami-123"
  instance_type = "t3.micro"

  ebs_block_device {
    device_name = "/dev/sdb"
    volume_size = 10
  }

  ebs_block_device {
    device_name = "/dev/sdc"
    volume_size = 20
  }
}
```

Using dynamic blocks:

```
variable "volumes" {
  default = [
    { device = "/dev/sdb", size = 10 },
    { device = "/dev/sdc", size = 20 }
  ]
}
```

```
resource "aws_instance" "server" {

  ami           = "ami-123"
  instance_type = "t3.micro"

  dynamic "ebs_block_device" {
    for_each = var.volumes

    content {
      device_name = ebs_block_device.value.device
      volume_size = ebs_block_device.value.size
    }
  }
}
```

Terraform automatically creates multiple EBS blocks.

---

# Using `iterator` (Optional)

You can rename the iterator variable.

Example:

```
dynamic "ingress" {
  for_each = var.ports
  iterator = port

  content {
    from_port = port.value
    to_port   = port.value
  }
}
```

Instead of:

```
ingress.value
```

You use:

```
port.value
```

# When Dynamic Blocks Are Useful

Dynamic blocks are commonly used for:

|Use Case|Example|
|---|---|
|Security group rules|ingress / egress|
|Load balancer listeners|listener blocks|
|EBS volumes|ebs_block_device|
|IAM policies|statement blocks|
|Subnet definitions|route tables|

---

# Dynamic Block vs for_each

|Feature|dynamic|for_each|
|---|---|---|
|Purpose|generate nested blocks|create multiple resources|
|Used in|inside resources|resource level|
|Example|ingress blocks|multiple EC2 instances|

Example:

```
dynamic → multiple ingress rules
for_each → multiple EC2 instances
```

# Real Production Example

Security groups often have **many rules**.

Bad approach:

```
20 ingress blocks manually
```

Better approach:

```
list of rules → dynamic block
```

Example variable:

```
variable "security_rules" {
  default = [
    { port = 80, cidr = "0.0.0.0/0" },
    { port = 443, cidr = "0.0.0.0/0" },
    { port = 22, cidr = "141.35.126.158/32" }
  ]
}
```

Dynamic block:

```
dynamic "ingress" {
  for_each = var.security_rules

  content {
    from_port   = ingress.value.port
    to_port     = ingress.value.port
    protocol    = "tcp"
    cidr_blocks = [ingress.value.cidr]
  }
}
```

This makes Terraform code **clean and scalable**.

---

# Important Points to Remember

- Dynamic blocks **generate nested blocks dynamically**.
- Used when a resource requires **multiple repeated configuration blocks**.
- Works with **lists, maps, and sets**.
- Syntax structure:

```
dynamic → for_each → content
```

- `block_name.value` refers to the **current item in iteration**.
- Often used for **security groups, volumes, listeners, IAM policies**.
