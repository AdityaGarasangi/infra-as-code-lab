- **Locals** (local values) allow you to **assign a name to an expression** and reuse that value multiple times within the same Terraform module.
- They help **avoid repeating the same expressions**, making Terraform configurations **cleaner, easier to maintain, and more readable**.
- Locals behave similar to **temporary variables inside a module**, but unlike input variables they **cannot be overridden by users**.

Basic syntax:

```
locals {
  name = expression
}
```

Example:

```
locals {
  app_name = "web-server"
}
```

Usage:

```
tags = {
  Name = local.app_name
}
```

---

- Multiple local values can be defined inside a single `locals` block.

Example:

```
locals {
  app_name   = "web"
  env        = "dev"
  owner      = "devops"
}
```

Usage:

```
tags = {
  Name        = local.app_name
  Environment = local.env
  Owner       = local.owner
}
```

---

- Locals are referenced using:

```
local.<name>
```

Example:

```
local.app_name
```

---

- Locals are often used to **build reusable values derived from variables**.

Example:

```
variable "environment" {
  default = "dev"
}
```

```
locals {
  instance_name = "${var.environment}-web-server"
}
```

Usage:

```
tags = {
  Name = local.instance_name
}
```

Result:

```
dev-web-server
```

---

- Locals are commonly used for **reusable tagging structures**.

Example:

```
locals {
  common_tags = {
    Environment = "dev"
    Project     = "terraform-lab"
    Owner       = "devops"
  }
}
```

Usage:

```
resource "aws_instance" "web" {
  ami           = "ami-123"
  instance_type = "t3.micro"

  tags = local.common_tags
}
```

This avoids repeating the same tags across multiple resources.

---

- Locals can also **combine variables and functions** to compute values dynamically.

Example:

```
variable "environment" {
  default = "dev"
}
```

```
locals {
  name_prefix = lower("${var.environment}-app")
}
```

Usage:

```
tags = {
  Name = local.name_prefix
}
```

Result:

```
dev-app
```

---

- Locals can contain **complex expressions and data structures** like lists and maps.

Example:

```
locals {
  allowed_ips = [
    "141.35.126.158/32",
    "10.0.0.0/16"
  ]
}
```

Usage:

```
cidr_ipv4 = local.allowed_ips[0]
```

---

- Multiple `locals` blocks can exist in a module, and Terraform automatically merges them.

Example:

```
locals {
  env = "dev"
}
```

```
locals {
  owner = "devops"
}
```

Terraform treats them as:

```
locals {
  env   = "dev"
  owner = "devops"
}
```

---

- Locals are **only accessible inside the module where they are defined**.

They cannot be accessed from:

- other modules
- parent modules
- child modules

If a value needs to be shared across modules, it should be passed using **variables or outputs**.

---

- Locals are evaluated **once during Terraform plan**, and their values remain constant during execution.

---

- A common pattern is to use locals to **standardize naming conventions**.

Example:

```
variable "environment" {
  default = "dev"
}

variable "project_name" {
  default = "inventory"
}
```

```
locals {
  resource_prefix = "${var.project_name}-${var.environment}"
}
```

Usage:

```
tags = {
  Name = "${local.resource_prefix}-ec2"
}
```

Result:

```
inventory-dev-ec2
```

---

- Another common pattern is using locals for **derived values used across multiple resources**.

Example:

```
locals {
  ssh_port  = 22
  https_port = 443
}
```

Usage:

```
from_port = local.ssh_port
```

---

- Locals are useful when:

|Use Case|Example|
|---|---|
|Avoid repeating values|common tags|
|Build naming conventions|resource prefixes|
|Store computed values|environment-based names|
|Combine variables|formatted identifiers|

---

- Key difference between **variables and locals**:

|Feature|Variables|Locals|
|---|---|---|
|Purpose|Input values|Computed reusable values|
|Can be overridden|Yes|No|
|Defined by|User / tfvars|Terraform configuration|
|Scope|Module input|Module internal|
