## What is HashiCorp Vault?

**HashiCorp Vault** is a tool used to **securely store, manage, and control access to secrets**.

Secrets include:

- API keys
- passwords
- database credentials
- tokens
- certificates

---

# Why Vault is Used

Vault solves problems like:

- Hardcoding secrets in code ❌
- Storing secrets in plain text ❌
- Poor access control ❌

👉 It provides **centralized, secure secret management**.

---

# Core Features

## 1. Secure Secret Storage

Stores secrets in an **encrypted format**.

---

## 2. Dynamic Secrets

Generates **temporary credentials on demand**.

Example:

- DB username/password valid for **1 hour only**

---

## 3. Access Control (Auth + Policies)

Controls **who can access what** using:

- Tokens
- IAM
- Kubernetes auth
- LDAP

---

## 4. Secret Leasing & Rotation

- Secrets **expire automatically**
- Can be **rotated regularly**

---

## 5. Encryption as a Service

Vault can **encrypt/decrypt data without storing it**.

---

# How Vault Works (Simple Flow)

1. User/app authenticates to Vault
2. Vault verifies identity
3. Vault checks policies
4. Vault returns secret (if allowed)

---

# Example (CLI)

### Store Secret

vault kv put secret/db password=admin123

---

### Read Secret

vault kv get secret/db

---

# Vault with Terraform

Terraform can fetch secrets from Vault using a **data source**.

```
data "vault_generic_secret" "db" {  
  path = "secret/db"  
}  
  
resource "aws_db_instance" "db" {  
  password = data.vault_generic_secret.db.data["password"]  
}
```
---

|---|---|---|

# Important Points

- Vault is **external to Terraform**.
- Terraform **should not store secrets directly**.
- Best practice → **fetch secrets from Vault at runtime**.
- Requires setup (server, auth methods, policies).

# Terraform + HashiCorp Vault Integration

## Goal

Use **HashiCorp Vault** to securely provide secrets to **Terraform**  
👉 instead of hardcoding them in `.tf` files.

---

# 3 Common Integration Approaches

## 1. Vault as a Data Source (Most Common)

Terraform **reads secrets from Vault at runtime**.

### Step 1: Configure Vault Provider

```
provider "vault" {  
  address = "http://127.0.0.1:8200"  
  token   = var.vault_token  
}
```

---

### Step 2: Read Secret

```
data "vault_kv_secret_v2" "db" {  
  mount = "secret"  
  name  = "db"  
}
```

---

### Step 3: Use Secret

```
resource "aws_db_instance" "db" {  
  password = data.vault_kv_secret_v2.db.data["password"]  
}
```

---

### Flow

```
Terraform → Vault → Secret → Terraform → Resource
```

---

## 2. Dynamic Secrets (Advanced + Powerful)

Vault can generate **temporary credentials on demand**.

### Example: AWS Dynamic Credentials

```
provider "vault" {  
  address = "http://127.0.0.1:8200"  
}  
  
data "vault_aws_access_credentials" "creds" {  
  role = "terraform-role"  
}
```
Use it:

```
provider "aws" {  
  access_key = data.vault_aws_access_credentials.creds.access_key  
  secret_key = data.vault_aws_access_credentials.creds.secret_key  
}
```

---

### Why this is 🔥

- Credentials auto-expire
- No long-term secrets
- Very secure

---

## 3. Vault for Terraform Authentication

Instead of storing cloud creds:

👉 Terraform **authenticates to Vault**, and Vault gives cloud access.

Used in:

- CI/CD pipelines
- Kubernetes
- Enterprise setups

---

# Authentication Methods (Important)

Vault supports multiple auth methods:

|Method|Use Case|
|---|---|
|Token|Simple/local dev|
|AppRole|CI/CD pipelines|
|IAM|AWS-based auth|
|Kubernetes|Pods accessing Vault|

---

# Best Practice Setup (Real-World)

👉 This is what companies actually do:

1. Store secrets in Vault
2. Terraform reads secrets dynamically
3. Use **short-lived credentials**
4. Never store secrets in:
    - `.tf` files ❌
    - `.tfstate` (as much as possible) ❌

---

# Security Notes (VERY IMPORTANT)

- Terraform state may still contain secrets ⚠️
- Always use:
    - Remote backend
    - Encryption
- Prefer **dynamic secrets over static secrets**
