- Terraform does **not execute `.tf` files in the order they appear in the directory**.
- Instead, Terraform **loads all `.tf` files in a directory together and treats them as one combined configuration**.

Example:

```
main.tf
variables.tf
network.tf
security.tf
outputs.tf
```

Terraform internally merges them as if they were **one large file**.

So file names like:

```
01-network.tf
02-compute.tf
```

are only for **human readability**, not execution order.

---

- Because Terraform merges all `.tf` files, **resources can reference each other across files**.

Example:

`network.tf`

```
resource "aws_vpc" "main" {
  cidr_block = "10.0.0.0/16"
}
```

`compute.tf`

```
resource "aws_instance" "web" {
  subnet_id = aws_vpc.main.id
}
```

Even though the VPC is defined in a different file, Terraform **can still resolve it automatically**.

---

- Terraform determines **execution order based on dependencies**, not file order.

Example:

```
resource "aws_subnet" "public" {
  vpc_id = aws_vpc.main.id
}
```

Dependency graph:

```
aws_vpc.main
     ↓
aws_subnet.public
```

Terraform automatically creates:

```
VPC → Subnet
```

This is called the **Terraform Dependency Graph**.

---

- Dependencies are automatically created when a resource **references another resource attribute**.

Example:

```
subnet_id = aws_subnet.public.id
```

Terraform understands:

```
Subnet must exist before EC2 instance
```

---

- Sometimes dependencies are not obvious. In such cases you can **manually define dependency using `depends_on`**.

Example:

```
resource "aws_instance" "web" {
  ami           = "ami-123"
  instance_type = "t3.micro"

  depends_on = [aws_security_group.tf_firewall]
}
```

This forces Terraform to create the **security group before the instance**.

---

- Terraform loads files in this approximate internal order:

1. **Terraform settings block**

```
terraform {
  required_providers
  backend
}
```

1. **Provider configuration**

```
provider "aws" {}
```

1. **Variables**

```
variable "region" {}
```

1. **Locals**

```
locals {}
```

1. **Data sources**

```
data "aws_ami" {}
```

1. **Resources**

```
resource "aws_instance" {}
```

1. **Outputs**

```
output "public_ip" {}
```

This is not strict file order, but **logical evaluation order**.

---

- Terraform also automatically loads specific files by naming convention.

Special files Terraform loads automatically:

|File|Purpose|
|---|---|
|`terraform.tf`|Terraform configuration|
|`terraform.tfvars`|Default variable values|
|`*.auto.tfvars`|Automatically loaded variable files|
|`*.tf`|All configuration files|

---

- Variable loading order also follows precedence.

Terraform loads variables in this order:

```
Environment variables
↓
terraform.tfvars
↓
*.auto.tfvars
↓
CLI -var or -var-file
```

Later sources **override earlier values**.

---

- Terraform also builds an **internal dependency graph** before running `apply`.

Execution flow:

```
Read configuration
↓
Merge all .tf files
↓
Build dependency graph
↓
terraform plan
↓
terraform apply
```

---

- Terraform uses **parallel execution when possible**.

Example:

If two resources have **no dependency**, Terraform may create them simultaneously.

```
VPC
 ├── Subnet A
 └── Subnet B
```

Subnet A and Subnet B can be created **in parallel**.

This improves infrastructure provisioning speed.

---

- If a dependency exists, Terraform enforces the order.

Example:

```
VPC
 ↓
Subnet
 ↓
EC2 Instance
```

Terraform will strictly follow this order.

---

### Important Points to Remember

- Terraform **does not execute files sequentially**.
- All `.tf` files in a directory are **merged into a single configuration**.
- Execution order is based on the **dependency graph**.
- Cross-file resource references **work automatically**.
- Terraform can run **independent resources in parallel**.
- `depends_on` can be used when dependencies are not automatically detected.
