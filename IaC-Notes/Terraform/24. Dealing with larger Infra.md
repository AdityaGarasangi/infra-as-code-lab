### 1. Use `parallelism` Carefully

- Terraform applies resources in parallel by default to speed up execution.
    
- For large infra, too many simultaneous API calls can **hit provider rate limits**.
- Limit parallelism:
```
terraform apply -parallelism=10
```

- **Tip:** Adjust based on provider API limits (AWS, Azure, GCP).

---

### 2. Use Resource Targeting Sparingly

- `-target` can update specific resources to avoid affecting the whole infra.
    
- **Do not use `-target` as a standard workflow** — it can leave infrastructure in a partial state.
    

---

### 3. Break Infra Into Modules

- Split infrastructure into **logical modules** (network, compute, storage, security).
    
- Easier to manage, review, and **apply independently**.
    

Example structure:
```
modules/
  network/
  compute/
  security/
environments/
  dev/
  prod/
```
---

### 4. Separate Environments

- Use **different workspaces or folders** for dev, staging, prod.
    
- Prevents accidental changes to production:
```
terraform workspace new prod  
terraform workspace select prod
```

---

### 5. Use `depends_on` Only When Necessary

- Terraform auto-detects dependencies, but **explicit `depends_on`** can prevent errors in complex setups.
    
- Avoid overusing it, as it may **serialize execution unnecessarily**, slowing down apply.
    

---

### 6. Plan Before Apply

- Always run `terraform plan` first, ideally **saving the plan**:
```
terraform plan -out=tfplan  
terraform apply tfplan
```
- Ensures no accidental destructive changes to large infra.
    

---

### 7. Use State Locking

- For large infra with multiple users or pipelines, enable **remote state with locking**:
```
terraform {  
  backend "s3" {  
    bucket = "terraform-state"  
    key    = "prod/terraform.tfstate"  
    region = "us-east-1"  
    dynamodb_table = "terraform-lock"  
  }  
}
```

- Prevents multiple applies from running at the same time.
    

---

### 8. Use `create_before_destroy` Where Needed

- For critical resources, avoid downtime by ensuring **new resources are created before old ones are destroyed**:
```
lifecycle {  
  create_before_destroy = true  
}
```
---

### 9. Avoid Hitting API Limits

- For AWS: avoid creating hundreds of resources at once.
    
- Use **smaller batches** or **apply modules separately**.
    
- Monitor provider-specific API limits.
    

---

### 10. Manage Large States

- Keep state files **remote (S3, GCS, Azure Blob)**, not local.
    
- Use **state locking** to prevent corruption.
    
- Use `terraform state list` and `terraform state show` to inspect large states without applying.
    

---

### 11. Use `refresh-only` Plan for Safety

- To avoid unexpected changes, you can run:
```
terraform apply -refresh-only
```

- Updates Terraform state with **actual current infra** without modifying resources.
    

---

### 12. Version Control & Review

- Keep all Terraform code in **Git**.
    
- Use **PRs** to review large infra changes.
    
- Never apply directly to production without review.
    

---

### 13. Logging and Debugging

- Enable detailed logs for large infra:
```
TF_LOG=INFO terraform apply
```

- Helps track throttling, API errors, or dependency issues.
    

---

### 14. Incremental Changes

- Avoid massive all-in-one `apply` for large infra.
    
- Apply **module by module** or **resource groups**, so failures don’t impact everything.
    

---

### 15. Use Workspaces or Variable Overrides

- Keep environments separate using `terraform workspace` or environment-specific `.tfvars`.
    
- Ensures prod, staging, and dev remain isolated.
    

---
***In short:***
For large infra: **modularize, plan first, limit parallelism, use state locking, separate environments, batch changes**, and monitor API limits. Avoid `-target` as a routine tool and always prefer incremental, controlled applies.
